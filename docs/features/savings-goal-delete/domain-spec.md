## 2. Goal lifecycle (state machine)

States (derived, no status column): ABSENT, ACTIVE_EMPTY (balance 0, no ledger rows, no events), ACTIVE_FUNDED (balance > 0 or any ledger/event history), COMPLETED (balance >= target; `SavingsGoalCurrencyPolicy.isUnfinished` false), DELETED (= ABSENT again). No ARCHIVED state in this feature (future feature `savings-goal-archive`).

| From | Trigger | To | Owner |
|---|---|---|---|
| ABSENT | `createSavingsGoal` | ACTIVE_EMPTY | `SavingsGoalRepository.kt:30-33` (unchanged) |
| ACTIVE_* | `incrementSavingsGoalAmount` / sweep accept | ACTIVE_FUNDED / COMPLETED | unchanged |
| ACTIVE_EMPTY | delete | DELETED | `SavingsGoalRepository.deleteSavingsGoal` (section 3) |
| ACTIVE_FUNDED, COMPLETED | delete | REJECTED, state unchanged | same owner |
| ABSENT | delete retry | AlreadyAbsent (success-like, no change) | same owner |

Illegal: deleting a funded goal through any product path; any write to the three savings Room tables from outside their owners (`db_ownership_policy.yml`, delete entry `config/guards/db_ownership_policy.yml:2903-2916`, sweep entry `:2934-2945`).
Retry: a retried delete after success returns AlreadyAbsent; after Rejected it re-evaluates (state may have changed). Cancellation: if cancelled during the pre-transaction history read nothing was touched; if cancelled inside the transaction Room rolls back; `CancellationException` is rethrown, no result and no failure state. Process death mid-transaction: SQLite rolls back, goal intact, the UI re-reads on next collect; process death before the transaction leaves nothing behind. No pending-delete journal exists or is needed.

## 4. Invariants (each testable; single owner named)

- INV-1 (owner: repository delete + `SavingsGoalDeletionPolicy`) A goal is deleted only when EMPTY: `currentAmount == 0.0` (non-finite or negative = non-empty, fail closed), zero ledger rows for the id, zero DataStore events for the id.
- INV-2 (repository) Check and delete are one Room transaction; the balance and ledger facts come from rows read inside it (DataStore events are read just before it, see INV-17). The passed `SavingsGoal` contributes only its `id` (DAO deletes by PK, `SavingsGoalDao.kt:21-22`); its amounts and name are ignored, and the entity passed to `deleteGoal` is the one re-read in the transaction (G-2, KDoc).
- INV-3 (repository) `writeBarrier.checkWritesAllowed` runs first (`SavingsGoalRepository.kt:36` precedent); a blocked call mutates nothing and the VM emits the existing `WriteBlocked` event.
- INV-4 (repository) A rejected delete changes zero rows in `savings_goals`, ledger, plan and marker tables.
- INV-5 (repository) Deleting an absent id returns AlreadyAbsent, changes nothing, never throws, and cannot affect another goal (AUTOINCREMENT ids are not reused; verify against schema JSON 151).
- INV-6 (repository) A successful delete never changes `savings_sweep_month_acceptance` or the exact-tier ledger row count of OTHER goals; the month stays consumed (existing pin `SavingsSweepAcceptanceCoordinatorTest.kt:85-107`).
- INV-7 (repository + guard) The only product caller of `SavingsGoalDao.deleteGoal` is the owner; for an empty goal the cascade removes zero ledger rows and zero plans (assert counts).
- INV-8 (repository + coordinator) Delete vs in-flight sweep accept is serializable: (i) delete commits first -> accept returns `Rejected(SAVINGS_SWEEP_GOAL_NOT_FOUND)` (`:116-117`, or `SNAPSHOT_MISMATCH`), batch rolled back, no ledger/plan/marker/balance change; (ii) accept commits first -> delete returns `Rejected(SAVINGS_GOAL_DELETE_HAS_BALANCE)` or `_HAS_HISTORY`. Forbidden: any interleaving where a committed accept's ledger/plan rows are removed by cascade.
- INV-9 (repository) Delete vs in-flight contribution: if the delete commits first, `incrementSavingsGoalAmount` returns false (`SavingsGoalRepository.kt:42`) and the VM records no DataStore event (`SavingsGoalsViewModel.kt:418`); if the increment commits first, delete returns `Rejected(..._HAS_BALANCE)`; if the increment committed but the event is not yet written, delete is still rejected because balance > 0 (balance is the authoritative witness). No DataStore event may exist for a goal that a successful delete removed (monotonic balance, F-4, F-6).
- INV-10 (repository) Unreadable history fails closed: DataStore corrupt or an invalid ledger row (`SavingsContributionHistoryUnavailableException`, `:32,76,89`) -> for an EXISTING goal with zero balance and no ledger rows: `Rejected(SAVINGS_GOAL_DELETE_HISTORY_UNAVAILABLE)`, nothing deleted. An absent goal still returns AlreadyAbsent and a goal with balance > 0 still returns HAS_BALANCE (precedence in INV-18). Unavailable is never treated as "no history".
- INV-11 (VM `SavingsGoalsViewModel`, single place) After Deleted or AlreadyAbsent: `selectedGoal` is cleared if it has that id; any `smartRecommendations` / `sweepRecommendation` / `recommendationToConfirm`-driving state naming that id is dropped; aggregates are recomputed from remaining goals only (via the existing flow, `:136-207`, no duplicate explicit recompute unless a non-Room source changed). The screen-local `recommendationToConfirm` (`SavingsGoalsScreen.kt:45`) is cleared by the screen when its goal id leaves `state.goals` (ux-flows section 3).
- INV-12 (repository + VM) `CancellationException` is rethrown unchanged at every catch; it never becomes a result, a failure state, a log reason or a user message (`UiWriteGuard.kt:23-24`; coordinator precedent `:183-184`).
- INV-13 (repository + VM) The delete API never throws except cancellation and `DatabaseAccessBlockedException`; every other failure is `Rejected(SAVINGS_GOAL_DELETE_UNAVAILABLE)`. The VM never lets an exception escape `viewModelScope.launch` (fixes F-1).
- INV-14 (repository + VM) Diagnostics are bounded codes only: `SAVINGS_GOAL_DELETE_HAS_BALANCE | _HAS_HISTORY | _HISTORY_UNAVAILABLE | _UNAVAILABLE` plus the existing `WRITE_BLOCKED`. Logs and UI state carry no goal name, amount, id, exception message, SQL text or stack. At most the exception class simple name (`UiWriteGuard.kt:35`).
- INV-15 (repository) Deleting an empty goal leaves `totalSaved` and level unchanged (balance 0) and leaves all other goals' rows bit-identical.
- INV-16 (no rule duplication) UI eligibility display calls the same `SavingsGoalDeletionPolicy` through the read-only eligibility member (section 3); no emptiness test exists in the VM or Compose code.
- INV-17 (repository; concurrency refinement from impact-map section 4) Fact-gathering order and the balance-as-witness rule. (a) DataStore history is read BEFORE the transaction so the Room write lock is never held across DataStore I/O. (b) Inside the transaction the goal row (balance) and the ledger rows for the id are re-read and re-checked; the in-transaction balance is the authoritative witness. (c) Soundness: balance never decreases (F-4); an event is recorded only after a successful positive increment (F-6); ledger rows are inserted in the same transaction as the balance CAS. Hence any event or ledger row that appears after the pre-read implies balance > 0 inside the transaction -> `Rejected(HAS_BALANCE)`. Events that existed before the pre-read are seen by it (`HAS_HISTORY`). Events pruned by 730d/5000 retention cannot make a funded goal deletable because balance still blocks. (d) The in-transaction ledger re-read (`ledgerDao.getAll()` filtered by goalId) closes the residual case of a ledger row with balance still 0 committed after the pre-read.
- INV-18 (`SavingsGoalDeletionPolicy`, single place) Rejection precedence for an existing goal: (1) balance is not exactly `0.0` (negative, NaN, +/-Infinity, or > 0) -> `HAS_BALANCE`; (2) any ledger row or event for the id -> `HAS_HISTORY`; (3) history unavailable -> `HISTORY_UNAVAILABLE`; else `Deletable`. Absent goal short-circuits to AlreadyAbsent before the policy. `-0.0` counts as zero.
- INV-19 (repository; guard identity) Every new member on the repository other than `deleteSavingsGoal` is a read whose name does not start with a mutation verb; the only DAO mutation reachable from `deleteSavingsGoal` is `savingsGoalDao.deleteGoal`; no new DAO delete/update/upsert query and no new `@Query`; callable identity unchanged (G-2). Verified by the db-ownership guard run on S2 (AE-23); failure -> STOP and escalate (SG-2).
- INV-20 (resources; owner: the string slice) Every new user-visible string key from `ux-flows.md` section 7 (9 keys) ships in `values`, `values-el` and `values-es` in the same change; no EN-only key; the lint MissingTranslation baseline never grows (int baseline = 2223 entries, cap derived from the baseline, never regenerate it; `verify_lint_baseline_policy.py:82-86`); each key is added only in the slice that references it (UnusedResources); VM/UI use `UiText.StringResource`, no raw literals; the goal name appears only as a format argument in the confirm dialog and the overflow content description.

## 5. Edge cases

- Mixed currencies / FX: the delete performs no conversion; emptiness is raw `currentAmount` in goal units, so missing or stale FX can never make a funded goal look empty. Unknown/legacy goal currency does not change eligibility (`SavingsGoalCurrencyPolicy` is irrelevant to the predicate).
- Unavailable vs zero: history unreadable is NOT zero history (INV-10, INV-18). A goal with unknown currency and balance 0 is still deletable.
- Rounding/conservation: no arithmetic. Deleting an empty goal changes no aggregate (INV-15).
- Time zones, DST, month-end: delete is time-independent. A delete on a sweep-window day leaves the month marker untouched (INV-6); a pending sweep card naming the goal is cleared on the next goals emission (`SavingsGoalsViewModel.kt:143-152`) and the accept pre-check rejects with `SAVINGS_SWEEP_STALE_RECOMMENDATION` (`:274-284`).
- Recurring / past items: savings goals have no recurring-rule, receipt or expense link; nothing to reconcile.
- Duplicates / idempotency: retried delete -> AlreadyAbsent. Double-tap on Confirm: second call sees ABSENT (and the dialog disables both buttons during Deleting).
- Stale snapshot: a UI holding an old goal object (balance 0) after a contribution landed must still be rejected (INV-2).
- Empty states: deleting the last goal returns the list to the existing empty state (`SavingsGoalsViewModel.kt:72-74`). UX-6: the header prints a hard-coded "Unavailable" for null level/total (`SavingsGoalsViewModel.kt:156`; `SavingsGoalsScreen.kt:288,312`). The implementer verifies what the header shows for zero goals; fix only if "Unavailable" (reads like an error) actually shows for an empty list, otherwise out of scope; either way pin the result with a VM test (AE-21).
- Partial failure: balance and history are separate stores for manual contributions (increment then DataStore write, `:415-427`); a failed history write leaves balance > 0 with no event. Such a goal is non-empty by balance, so delete stays blocked, which is the safe direction.
- Backup/restore/reset window: barrier blocks delete (INV-3). Restore of an older backup can re-introduce a deleted goal; that is existing behaviour, not a delete defect.
- Legacy imported goals may carry balance with no ledger or events (`M service/debug/LegacyDataMigrationService.kt:513-525`): non-empty by balance.
- Pre-read fails while the goal is also absent: AlreadyAbsent wins (INV-10); no error is surfaced for an already-gone goal.
- Transaction/DataStore cancellation points: the pre-read is a cancellation point with no side effects; the in-transaction reads and the delete roll back together (INV-12).
- `ledgerDao` nullable in the history repository (F-6): the in-transaction ledger check (INV-17 d) uses the injected non-null DAO directly, so a null-wired history repository can never hide ledger rows from the final check.

## 7. Privacy

Goal `name` is user text; an empty-goal delete removes it from the live DB entirely. Older backups still hold it (existing behaviour). Nothing new is stored. Logs and diagnostics: bounded codes only (INV-14); no names, amounts, ids, raw exception messages, paths or SQL. The goal name is held only in UI state for the confirm dialog and the overflow content description, never logged. No new permissions, no network.
