# Phase 2 — Time / Period Semantics Foundation Implementation Plan

Minor note: your audit footer says `Generated by Scout on 2026-05-01`; today is 2026-04-30, so I treated that as a label/date typo and used the audit content itself.

## Phase 2 Goal

Create one deterministic time model for the app:

1. All logical periods use half-open ranges: `[startInclusive, endExclusive)`.
2. All “current time” decisions use `TimeProvider.now()`.
3. Each logical calculation captures `now` once.
4. Calendar periods are calendar-aware, not `30/90/365 * DAY_IN_MILLIS`.
5. Bad/unknown dates are explicit errors, not silently rewritten to today.
6. Recurrence/forecast models do not encode calendar meaning through magic zero values.
7. Current-period flows refresh after day/month rollover.

## Non-goals

Do not combine Phase 2 with:

- currency Phase 1 changes, except conflict resolution
- Room schema/version migrations unless absolutely unavoidable
- a full timezone preference redesign
- hidden pagination fixes
- effectiveAmount / transfer-income semantics
- localization cleanup unrelated to dates
- broad UI redesign

Canonical timezone for this phase: device/system default timezone.

# Core Contract

## Allowed clocks

| Use case | Allowed source |
|---|---|
| Logical app time | `TimeProvider.now()` |
| Production implementation | `SystemTimeProvider.now()` only |
| Performance timing | `System.nanoTime()`, `TimeSource.Monotonic`, or existing perf utility |
| Android elapsed alarms | `SystemClock.elapsedRealtime()` |
| WorkManager repeat intervals | `Duration`/`TimeUnit`, not logical period math |

## Forbidden outside explicit whitelist

- `System.currentTimeMillis()`
- `Instant.now()`
- `LocalDate.now()`
- `LocalDateTime.now()`
- `Calendar.getInstance().get(Calendar.YEAR)` for “current year”
- raw logical day math: `(a - b) / 86_400_000`
- inclusive period ends: `23:59:59`, `23:59:59.999`
- calendar periods from fixed days: `30`, `90`, `365`

## TimePeriodUtils policy

`TimePeriodUtils` remains the canonical owner of local calendar math.

It may internally create a `Calendar` or use `java.time`, but every function must be seeded from an explicit timestamp. It should not fetch “now” itself.

Required helpers:

- `isInRange(timestamp, startInclusive, endExclusive)`
- `getDayRange(timestamp)`
- `getWeekRange(timestamp)` — Monday start
- `getMonthRange(timestamp)`
- `getQuarterRange(timestamp)`
- `getYearRange(timestamp)`
- `getStartOfDay(timestamp)`
- `getEndOfDay(timestamp)` = start of next day
- `getStartOfWeek(timestamp)`
- `getEndOfWeek(timestamp)` = start + 7 calendar days
- `getEndOfMonth(timestamp)` = start of next month
- `getEndOfQuarter(timestamp)` = start of next quarter
- `getEndOfYear(timestamp)` = Jan 1 of next year
- `addDays`, `addMonths`, `addYears`
- `daysBetween(start, end)` using local dates, DST-safe
- `formatMonthKey(timestamp)` using canonical `yyyy-MM`
- `parseMonthKeyToRange(monthKey)`
- `buildMonthKeyRange(startMonthKey, endMonthKey)`
- `getCanonicalWeekRangeFromKey(weekKey)`

Deprecate ambiguous `getLastNDaysRange()` and replace with explicit helpers:

- `getLastNCalendarDaysRange(now, days)`  
  Full local calendar days, inclusive of today, end = tomorrow start.
- `getLastNCompleteDaysRange(now, days)`  
  Complete days ending at today start.
- `getTrailingElapsedRange(now, days)`  
  Exact elapsed duration only, not for calendar reports.

# Acceptance Criteria

Phase 2 is done when:

1. `TimePeriodUtils` documents and enforces half-open periods.
2. All calendar period queries use `[start, end)`.
3. Production logical code no longer directly calls wall-clock APIs outside whitelist.
4. Entity timestamps are explicit at creation boundaries.
5. Invalid parser/import dates do not fallback to today.
6. “This Month/Quarter/Year” use calendar ranges.
7. Rolling windows are explicitly named rolling windows.
8. Raw millis day division is gone from logical day calculations.
9. Weekly aggregates expose canonical Monday-start ranges.
10. Day-of-week analytics are Monday→Sunday.
11. Forecast/recurrence no longer use magic zero temporal sentinels.
12. Current-period flows refresh across day/month rollovers.
13. `TestUtils.endOfMonth()` follows half-open semantics.
14. Targeted tests and compile pass.
15. Docs/registry are updated only for verified fixes.
