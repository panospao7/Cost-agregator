| 1 | `data/database/dao/SplitItemAssignmentDao.kt` | MAJOR | SQL correctness | `getParticipantTotals()` groups only by `participantName`. If two assignees share the same display name, their rows are merged into one total even though `participantIndex` exists to distinguish them. **[DOWNGRADED]** | Group by a stable participant key (`participantIndex` + `participantName`, or a real participant ID) and return that key in `ParticipantTotal`. |
| 2 | `data/database/dao/MerchantNormalizationDao.kt` | MAJOR | Data integrity / query determinism | `getAliasByNormalizedKey()` uses `LIMIT 1` on a non-unique `normalizedKey`, while `linkAliasToCanonical()` upserts by `rawName`. That allows multiple rows for the same normalized key and makes alias resolution nondeterministic; user-defined remaps may not win consistently. **[RESOLVED BY B.4 — Batch 5]** Uniqueness enforced on `normalizedKey`; alias writes/reads use the same key. | Enforce uniqueness on `normalizedKey`, or make lookup deterministic (`ORDER BY isUserDefined DESC, occurrenceCount DESC`) and update/merge aliases by `normalizedKey` instead of `rawName`. |
| 3 | `data/database/dao/ExchangeRateDao.kt` | MAJOR | Index usage / performance | `getAllRatesForBase()` filters on `toCurrency` and orders by `fromCurrency`, but the schema only indexes `(fromCurrency, toCurrency)`. SQLite cannot efficiently use that composite index for `WHERE toCurrency = ?`, so this query will scan the table on every currency screen load/flow collection. **[RESOLVED BY B.4 — Batch 29 closeout: `Index(["toCurrency"])` entity annotation added to `ExchangeRate.kt`; `MIGRATION_78_79` creates `index_exchange_rates_toCurrency`; schema version 79; `MigrationContractTest.migration_78_to_79_adds_toCurrency_index_on_exchange_rates` + `DatabaseMigrationTest.migrate_77_to_79_chain_passes_and_has_toCurrency_index` cover migration; table remains small so connected androidTest execution is waived per ISSUE-B4-WAIVER]** | Add an index such as `(toCurrency, fromCurrency)`, or change the query/storage contract so the filtered column is the leading indexed column. |
| 4 | `data/database/dao/ManualRecurringExpenseDao.kt` | MAJOR | DAO contract correctness | The "dual API" pair is inconsistent: `getAllFlow()` orders by `nextDate ASC`, but `getAll()` orders by `createdAt DESC`. Callers switching between reactive and one-shot APIs get different result ordering for the same dataset. **[DOWNGRADED]** | Make both methods use the same ordering, or rename/split them so the different semantics are explicit. |

| 6 | `app/src/main/java/com/yourname/expensetracker/data/database/dao/ExpenseGroupDao.kt:73-92` | MAJOR | Transaction boundary / DAO contract | `insertGroupWithMembers()` wraps work in an `ExpenseGroupDao` `@Transaction`, but the second half of the write is delegated through a caller-supplied `GroupMemberDao`. Future callers/tests can treat this as a safe atomic DAO helper when it is really a fragile cross-DAO shortcut. **[DOWNGRADED — method is unused in production; atomicity fragility is latent only]** | Remove this unused helper, or move the whole operation to a coordinator/repository that owns both DAOs and uses `AppDatabase.withTransaction { ... }`. |
| 7 | `app/src/main/java/com/yourname/expensetracker/data/database/dao/GroupMemberDao.kt:38-39,57-58` | MAJOR | Data integrity / nondeterministic query | `getCurrentUserFlow()` and `getCurrentUser()` do `LIMIT 1` with no `ORDER BY`, but `group_members` only has a non-unique `(groupId, isCurrentUser)` index. Nothing prevents two members in the same group from having `isCurrentUser = 1`, and `GroupTransactionCoordinator.addMemberToGroup()` (`data/database/GroupTransactionCoordinator.kt:83-103`) inserts new current-user rows without clearing an existing one. The DAO can therefore return an arbitrary "current user" for a group. **[RESOLVED BY B.4 — Batch 3]** Partial unique index added; transactional demote-then-promote write path enforced. | Enforce at most one current-user row per group (partial unique index or transactional demote-then-promote update), and make the lookup deterministic if duplicates must still be tolerated. |
| 8 | `app/src/main/java/com/yourname/expensetracker/data/database/dao/GroupExpenseDao.kt:60-77` | MAJOR | SQL correctness / cross-component integrity | `countPotentialSplitReferences()` is only a text-pattern prefilter: it strips literal spaces from `customSplitsJson` and then uses `LIKE`. `SharedExpenseManager` stores validated custom split payloads without canonicalizing whitespace (`domain/groups/SharedExpenseManager.kt:143-150`), so tabs/newlines can still be persisted and parsed correctly later. In `GroupsRepositoryImpl.deleteMember()` (`data/repository/GroupsRepositoryImpl.kt:163-173`), a false negative from this query skips the full parser inside the transaction, which can allow deleting a member that is still referenced in custom splits. **[FALSE POSITIVE — current writers serialize custom split payloads canonically with no tabs/newlines; the reported whitespace false-negative path is not reachable from present code paths]** | Canonicalize split payloads before storing them, or drop the SQL text prefilter and always parse candidate expenses inside the transaction before deleting a member. |
| 9 | `app/src/main/java/com/yourname/expensetracker/data/database/dao/GroupExpenseDao.kt:33-34` | MAJOR | Data integrity / query determinism | `getGroupExpenseForExpense()` assumes a single `group_expenses` row per linked `expenseId` by returning `LIMIT 1`, but `GroupExpense` only indexes `expenseId` and does not make it unique (`data/database/entity/GroupExpense.kt:34-38`). If duplicate links are inserted, callers get an arbitrary row and the one-to-one "system expense -> group expense" contract silently breaks. **[DOWNGRADED — duplicate-producing insert path not active today; RESOLVED uniqueness enforcement was RESOLVED BY B.4 — Batch 3 at entity level]** | Add a unique constraint/index for non-null `expenseId`, or change the DAO contract to return all matches and have callers handle duplicates explicitly. |
| 10 | `app/src/main/java/com/yourname/expensetracker/data/database/dao/BankConnectionDao.kt:36-37` | MAJOR | Security / credential lifecycle | `disconnect()` marks a bank connection inactive/disconnected but leaves `accessToken`, `refreshToken`, and `tokenExpiry` in place. That preserves valid credentials after the user disconnects and leaves the DB state inconsistent: the row says "disconnected" while still carrying reusable tokens. **[RESOLVED BY B.4 — Batch 6]** Token fields nulled out in the disconnect update. | Clear sensitive token fields as part of the disconnect update (`accessToken = NULL`, `refreshToken = NULL`, `tokenExpiry = NULL`) and, if needed, reset sync/error metadata in the same statement. |
| 11 | `app/src/main/java/com/yourname/expensetracker/data/database/dao/EmailReceiptDao.kt:15-16` | MAJOR | Upsert semantics / provenance integrity | `insert()` uses `OnConflictStrategy.REPLACE` even though `emailMessageId` is unique (`data/database/entity/EmailReceiptSource.kt:23-29`). `EmailReceiptIngestionService` checks duplicates by fingerprint but never by message ID before creating new receipt/source rows (`data/email/EmailReceiptIngestionService.kt:104-125,161-172`). Re-ingesting the same external email with a different fingerprint or parse result can therefore delete the old provenance row and relink that message ID to a brand-new receipt/expense instead of returning a duplicate. **[RESOLVED BY B.4 — Batch 6]** Deduplication by `emailMessageId` added before inserts; DAO changed to non-destructive semantics. | Deduplicate by `emailMessageId` before any inserts, and change the DAO to `ABORT`/`IGNORE` (or an explicit upsert that preserves the existing `receiptId`) so a repeated message cannot overwrite earlier lineage. |

That pushes empty-portfolio handling onto every caller and makes these aggregates easy to misuse; there are no DAO tests covering the zero-row case. **[FALSE POSITIVE — nullable `Double?` return types accurately model `SUM(...)` on empty result sets; no current caller assumes these queries are non-null]** | Use `COALESCE(SUM(...), 0.0)` in all three queries and return non-nullable `Double` values. |
