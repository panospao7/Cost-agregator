## Key Patterns

### 1. Identity-Provide Anti-Pattern (Critical)
**Recurring in: `SubscriptionModule`, `OcrImprovementsModule`, `GroupsModule`, `SavingsModule`, `AiModule`**

The most pervasive issue is the pattern:
```kotlin
@Provides @Singleton
fun provideFoo(foo: Foo): Foo = foo
```
When `Foo` already has `@Inject constructor`, this creates **duplicate Dagger bindings**. In the identity-provide form (`SubscriptionModule`, `OcrImprovementsModule`), Dagger must use `Foo`'s `@Inject constructor` to satisfy its own `@Provides` parameter, making the `@Provides` method a pure no-op that creates binding ambiguity. In the manual-construction form (`AiModule`, `GroupsModule`), Dagger has two distinct ways to build the same type. **These should all be removed** — `@Inject constructor` with `@Singleton` on the class is sufficient.

### 2. Unmanaged CoroutineScopes in Singletons
**Found in: `ExpenseTrackerApp`, `TransactionClassifier`, `BudgetMonitor`**

Multiple singletons create their own `CoroutineScope(SupervisorJob() + Dispatchers.X)` instead of using the DI-provided `@ApplicationScope`. These scopes are: (a) not tied to any lifecycle, (b) cancelled on `onStop()` but never recreated, making the singleton unusable after the first background cycle, (c) inconsistent in dispatcher choice (`Default` vs `IO`).

### 3. Layer Violations in Domain-Layer Engines
**Found in: `SavingsModule`, `SmartSavingsEngine`, `AutomatedSavingsRuleEngine`**

Domain-layer classes directly depend on `data.repository.SavingsGoalRepository` (concrete class) instead of `domain.savings.SavingsGoalRepository` (interface), despite a binding module (`SavingsRepositoryBindingsModule`) existing to bridge them.

### 4. Over-Scoped Singletons
**Found in: `DaoModule` (43+ DAOs), `ExportModule`, `EmailIngestionModule`**

Stateless or lightweight objects are scoped as `@Singleton`, preventing garbage collection and increasing the permanent memory footprint. Room DAOs and stateless parsers/exporters do not benefit from singleton scoping.
