### Per-File Issues
| # | File:Line | Severity | Type | Description | Suggested Fix |
|---|-----------|----------|------|-------------|---------------|
| 1 | domain/logic/SplitCalculator.kt:229-239 | CRITICAL | Bug | `toCents()` converts money to `Int`, so totals above ~€21.47M overflow into negative cents. The existing stress test already documents corrupted split outputs for `25_000_000.00`. | Store cents in `Long` (or the project `Money` type) end-to-end and keep all split math in integer minor units. |
| 2 | domain/forecasting/FinancialStressForecastEngine.kt:183-214 | HIGH | Bug | `calculateRecurringOutflows()` only counts patterns when `nextExpectedDate` is already inside `[startDate, endDate]`. If a pattern's next date is stale but still recurring, the code never advances it into the horizon, so active bills disappear from the stress forecast. | Advance each pattern forward until it reaches `startDate` (or passes `endDate`) before counting occurrences. |
| 3 | domain/forecasting/FinancialStressForecastEngine.kt:223-239,443-459 | HIGH | Bug | The engine treats “current balance” as **this month's deposits minus this month's purchases**, and it can fall back to `totalBudget` as a proxy for income. Both are poor substitutes for actual cash on hand / actual income and can materially distort crunch probability. | Feed the engine a real balance/income source, or degrade the forecast when those inputs are unavailable instead of inferring them from budget caps and current-month net flow. |
| 4 | domain/forecasting/FinancialStressForecastEngine.kt:273-279 | HIGH | Bug | The discretionary Monte Carlo bootstrap drops zero-spend days and samples only from positive-spend days for every future day. That systematically inflates projected discretionary spend for users who do not spend daily. | Build the empirical daily distribution across the full lookback window, including zero-spend days, or model spend frequency separately from spend amount. |
| 5 | domain/forecasting/DataQualityAssessor.kt:72-96 | HIGH | Bug | An unusable distribution (`fit.isUsable == false`) can still score `HIGH` confidence if volume/density/recency are strong enough. The simulator can therefore return a deterministic fallback forecast labeled as highly trustworthy. | Hard-cap unusable fits at `LOW` (or at most `MODERATE`) confidence before applying the weighted score. |
| 6 | domain/forecasting/HistoricalSpendingDistribution.kt:130-165 | HIGH | Bug | Week/day bucketing uses fixed `24h` and `7*24h` millisecond division. Around DST transitions, transactions can slide into the wrong day/week bucket, which changes qualifying-week counts and fitted totals. | Group by calendar day/week boundaries via `Calendar`/`java.time`/`TimePeriodUtils` instead of raw millisecond division. |
| 7 | domain/logic/SynthesisEngine.kt:109-147 | HIGH | Bug | `totalCommitted` / `totalLikely` count each recurring pattern only once if its `nextExpectedDate` is inside the month. Weekly and biweekly bills that occur multiple times before month-end are understated in the synthesized forecast. | Expand recurring occurrences through `endOfMonthExclusive` and sum every in-range occurrence, not just the first one. |
| 8 | domain/logic/SynthesisEngine.kt:429-437 | HIGH | Bug | Biweekly recurrence matching treats any date within ±2 days of the cycle as a bill day. That can mark up to 5 days in a 14-day cycle as carrying the same bill, inflating daily targets and duplicate bill markers in Block Party. | Generate exact scheduled occurrence dates and map each occurrence to a single target day (or a single closest tolerated day), not a multi-day window. |
| 9 | domain/logic/RecurringExpenseEngine.kt:94-102 | HIGH | Bug | Detected `nextExpectedDate` is only `lastObserved + one interval`; it is not rolled forward to the next future occurrence. A monthly bill last seen 45 days ago produces a past-due next date and is then filtered out by downstream forecasting logic. | Repeatedly advance the predicted date until it lands at or after `timeProvider.now()` (optionally with a bounded grace window). |
| 10 | domain/logic/SplitCalculator.kt:67-83,94-105,117-128,153-165 | HIGH | Bug | Invalid custom splits silently fall back to equal splitting. That changes the financial meaning of stored expenses instead of surfacing bad legacy data, and it can corrupt balances/reimbursement math without any hard failure. | Return an explicit error/result for invalid persisted splits, or preserve the stored raw allocations for read-only legacy rendering instead of rewriting them as equal splits. |
| 11 | domain/forecasting/MonteCarloSpendingSimulator.kt:235-249 | MEDIUM | Bug | `countRecentQualifyingWeeks()` treats any recent week with `total > 0` as “qualifying”, even though `HistoricalSpendingDistribution` defines qualification as at least 3 distinct transaction-days. Recent sparse weeks therefore inflate confidence. | Carry forward week-level quality metadata from `HistoricalSpendingDistribution` and compute recency from the same qualification rule used for the fit. |
| 12 | domain/logic/CustomSplitParser.kt:121-143 | MEDIUM | Bug | Percent/amount tolerance checks use raw `Double` sums, so boundary-valid payloads like `33.3,33.3,33.3` or `60,20,19.99` can fail because of binary floating-point noise. The ignored tests in `CustomSplitParserTest` already point at this edge. | Compare rounded minor units / basis points with `BigDecimal` or integer math instead of direct `Double` tolerance checks. |
| 13 | domain/forecasting/ForecastModels.kt:N/A | LOW | Architecture | The approved batch plan references `ForecastModels.kt`, but no such file exists in the source tree. Forecast models are currently split across `MonteCarloResult.kt` and `domain/model/*`, which makes batch review/tooling drift-prone. | Either restore a dedicated `ForecastModels.kt` or update the batch plan/file map so it matches the actual source layout. |
| 14 | domain/logic/SynthesisModels.kt:N/A | LOW | Architecture | The approved batch plan references `SynthesisModels.kt`, but synthesis models actually live in `domain/model/FinancialForecast.kt` and `domain/model/BlockPartyDay.kt`. This creates the same review/tooling drift as the missing forecast models file. | Align the plan with the real file layout, or consolidate the synthesis models back into a dedicated file. |

### Cross-Component Issues
| # | Components | Severity | Type | Description | Suggested Fix |
|---|-----------|----------|------|-------------|---------------|
| 1 | RecurringExpenseEngine ↔ SynthesisEngine ↔ FinancialStressForecastEngine | HIGH | Bug | Both downstream engines rely on `nextExpectedDate >= today`, but `RecurringExpenseEngine` only advances one interval past the last observed payment. Any still-active pattern that is already one cycle overdue disappears from both synthesis and stress forecasting. | Centralize recurring-occurrence generation in one shared utility that always rolls patterns forward into the active forecast horizon. |
| 2 | CustomSplitParser ↔ SplitCalculator ↔ GroupsRepositoryImpl ↔ SharedExpenseManager | HIGH | Bug | Custom split validation is performed against the **current** group member set, not the member set at expense creation time. After membership changes, historical custom splits can become “invalid”, which then triggers equal-split fallback or incorrect delete-member reference checks. | Persist the participant snapshot (or membership version) on each group expense and validate historical splits against that snapshot instead of current membership. |
| 3 | FinancialStressForecastEngine ↔ MonteCarloSpendingSimulator | MEDIUM | Architecture | The codebase now has two separate Monte Carlo implementations for spending risk: one daily bootstrap inside `FinancialStressForecastEngine`, and one weekly log-normal simulator in `MonteCarloSpendingSimulator`. Similar features can therefore disagree on percentile/risk outputs. | Define one canonical simulation engine (or clearly separate contracts with non-overlapping use-cases) and reuse its sampling/percentile logic. |
| 4 | CustomSplitParser ↔ SharedExpenseBudgetOffsetEngine | HIGH | Bug | Core group-expense flows use the strict parser, but budget-offset logic still reparses `customSplitsJson` with a permissive raw `split(':')` routine. Malformed payloads can therefore be rejected in one path and partially accepted in another. | Route every custom-split read through `CustomSplitParser` (or a shared canonical decoder) so all group-expense features apply the same validation semantics. |

### Overlapping Functionality
| # | Files | Description | Recommendation |
|---|-------|-------------|----------------|
| 1 | FinancialStressForecastEngine.kt, MonteCarloSpendingSimulator.kt | Two separate Monte Carlo pipelines implement their own sampling assumptions, deterministic seeding, and percentile extraction. | Consolidate Monte Carlo logic behind one shared simulator/service and make callers supply scenario-specific inputs. |
| 2 | SynthesisEngine.kt, FinancialStressForecastEngine.kt | Recurring-expense scheduling/occurrence logic is duplicated across synthesis and stress forecasting, with different counting semantics. | Extract a shared recurring-occurrence expander and reuse it in both engines. |
