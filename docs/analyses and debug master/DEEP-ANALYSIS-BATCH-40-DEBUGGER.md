## Key Patterns

### 1. Split Calculation Divergence (Systemic)
The most impactful pattern is the **dual split-calculation code paths**. `SharedExpenseBudgetOffsetEngine` uses naive floating-point division for equal splits while `SharedExpenseManager` uses proper cent-based arithmetic. This means the budget view and the group balance view produce slightly different numbers for the same expenses.

### 2. Hardcoded `System.currentTimeMillis()` (3 instances)
`SharedExpenseManager.addExpense`, `AddGroupExpenseUseCase`, and `GroupsRepository.addExpenseWithLink` all use `System.currentTimeMillis()` directly instead of injected `TimeProvider`. This makes time-dependent behavior untestable.

### 3. Locale-Dependent Calendar Arithmetic
`HistoricalSpendingDistribution.computeDistribution()` relies on `Calendar.set(DAY_OF_WEEK, MONDAY)` which is sensitive to the device's locale `firstDayOfWeek` setting. On US-locale devices where Sunday is the first day of the week, running on Sundays produces incorrect week boundaries.

### 4. Overdue Recurring Pattern Gap
`FinancialStressForecastEngine.calculateRecurringOutflows` fails to advance overdue patterns forward into the forecast horizon. If a pattern's `nextExpectedDate` is before `startDate`, it is completely skipped, understating recurring obligations.

### 5. Domain/Data Layer Blurring
Three domain-layer files import directly from `data.database.entity` and `data.repository`, while `SharedExpenseManager` properly uses the `SharedExpenseDataPort` domain interface. This inconsistency creates two parallel data access patterns that can diverge in behavior.
