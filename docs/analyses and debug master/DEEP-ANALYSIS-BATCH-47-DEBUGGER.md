## Key Patterns

### 1. Domain-Data Layer Boundary Violations (Systemic)
Multiple domain model files directly import data-layer types (`Expense`, `TransactionType`, `OwnershipFilter`). This pattern is widespread in the codebase (30+ domain files import `TransactionType` from the data layer). The domain layer is not properly isolated — it's a "leaky domain" where data entity knowledge penetrates into models and mappers.

### 2. Non-deterministic Default Values (Recurring Anti-pattern)
Three files use `System.currentTimeMillis()` or `UUID.randomUUID()` as data class default parameter values: `DomainTransactionFilter.correlationId`, `DashboardFollowThroughRecommendation.id`, `DashboardFollowThroughRecommendation.createdAt/updatedAt`. This poisons `equals()`/`hashCode()` for data classes, makes tests non-deterministic, and breaks caching/deduplication.

### 3. Copy() Semantics with Cross-field Dependencies
`DashboardFollowThroughRecommendation.expiresAt` depends on `createdAt` in its default expression, but Kotlin's `copy()` does not re-evaluate defaults. This is a well-known Kotlin data class pitfall where derived fields become stale after partial copies.

### 4. Lossy Round-trip Conversions
The `DashboardExpense → Expense` mapper drops ~20 fields, creating reconstituted entities with incorrect computed properties (`effectiveAmount`). The serializer drops `correlationId`. Both represent information loss in conversion pipelines that silently produce incorrect downstream results.

### 5. Mixed Numeric Types for Financial Data
The batch mixes `Double`, `Float`, and `Int` for financial amounts, percentages, and risk levels. This causes silent precision loss (`Float` has only ~7 significant digits vs `Double`'s ~15) and makes the API inconsistent across models.
