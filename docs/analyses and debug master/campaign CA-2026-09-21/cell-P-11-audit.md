## New findings

### CA-P-11-001 | Conflicting ISO currencies fall through to a domain default

- Defect class: **13** (staged/dead-path classification required by governing section 4; underlying class 7 money/currency, class 15 fix-regression).
- Severity: **P3**. No current production reach; this is a parser defect, not a request to wire the feature.
- Evidence at pin: `app/src/main/java/com/yourname/expensetracker/data/email/provider/EmailReceiptParser.kt`, `BaseEmailParser.detectCurrencyCode`, **309–322**: only `isoMatches.size == 1` returns; `size > 1` falls through to `trustedDomainCodes` instead of rejecting. `AmazonReceiptParser.kt`, `detectCurrency`, **144–149**, passes its domain map (**44–50**). `AppleReceiptParser.kt`, `detectCurrency`, **199–204**, does likewise with **27–30**. `LEGAL_PATHS.md`, Email Receipt Parsing, **232–237**, explicitly promises that conflicting ISO codes fail.
- Impact path: static example `Order Total: 12.34 EUR\nConverted: 13.50 USD\namazon.com` has no currency symbol, two ISO matches, and a recognized domain. The parser returns amount 12.34 with currency USD instead of a controlled unresolved outcome. In the staged path: provider parse → service validation (only positive amount/nonblank merchant/positive date, **367–370**) → fingerprint and EmailReceiptData → receipt coordinator **1026–1040**, and, with sufficient date/order confidence, expense request **1157–1170**. It can mislabel stored monetary amounts if invoked; no present user effect is claimed.
- Caller trace: **NONE-FOUND** for a production entry. Main-source searches found provider constructors in `EmailIngestionModule` and `EmailReceiptIngestionService`, service-internal batch calls, and the service→coordinator edge only. No service injection/transport/worker/UI entry.
- Existing tests/guards: `EmailReceiptParserTest.kt` **89–104** checks `USD or EUR` with the default EMPTY domain map, so it cannot expose the domain fallthrough. It tests trusted domains separately, without conflicting codes. Architecture ownership/barrier guards do not enforce parser currency semantics. No execution performed.
- Cross-cell impact: P-03 receipt storage and P-02 expense creation are downstream consumers if staging ends; no shared currency engine defect asserted.
- Old-ID cross-refs: **none (same issue)**. FRESH-P11-002 concerns removed two-letter tokens; RP-18's accepted whole-body symbol priority concerns symbol selection, not failure to reject conflicting ISO codes. The faulty branch was added by `22b82b2c` (RP-18 18-A).

### CA-P-11-002 | Aggregate summary rows bypass the total-selection exclusion

- Defect class: **13** (staged/dead-path classification; underlying class 7 money/parser correctness, class 15 fix-regression).
- Severity: **P3**. No current production reach.
- Evidence at pin: `app/src/main/java/com/yourname/expensetracker/data/email/provider/EmailReceiptParser.kt`, `extractTotalAmount` **221–226**, `extractLabeledLineAmount` **233–244**, `extractKeywordLineTotal` **247–252**, `extractStrictAmount` **260–265**, and `isSummaryRow` **325–328**. Total extraction never calls `isSummaryRow`; the keyword fallback accepts any amount on a line containing `total`. `LEGAL_PATHS.md`, Email Receipt Parsing, **230–232**, explicitly excludes aggregate rows from totals as well as items.
- Impact path: static input `3 items, total 45,90 EUR` → no anchored total label → keyword fallback → 45.90 accepted. That same line is intentionally recognized as a summary by `isSummaryRow`. A partial receipt containing only a per-group summary (plus date/order metadata) can therefore become a whole-receipt total, obtain sufficient confidence, and pass service validation → coordinator receipt/expense amount. A later valid specific total still wins; the defective case is absent/unparseable specific totals.
- Caller trace: **NONE-FOUND** for a production entry; service → all three provider parsers → shared total helpers. Staging absence is intentional D2 behavior, not this finding.
- Existing tests/guards: `EmailReceiptParserTest.kt` **108–113** checks `isSummaryRow("3 items, total 45,90")` independently; **52–85** exercises total extraction without an aggregate summary. Provider summary tests assert item exclusion, not total rejection (`AmazonReceiptParserTest.kt` test at **112**; `AppleReceiptParserTest.kt` test at **257**). No static ownership guard covers numerical selection. No execution performed.
- Cross-cell impact: P-03/P-02 downstream receipt/expense amounts if invoked; no changes to those cells requested.
- Old-ID cross-refs: **none (same issue)**. FRESH-P11-007 concerns phantom line items, not accepting a group summary as the receipt total; that item skip is present at the pin. The new shared helper was introduced by `22b82b2c`.
