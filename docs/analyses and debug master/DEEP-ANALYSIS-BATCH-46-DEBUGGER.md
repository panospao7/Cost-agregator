## Key Patterns

### 1. Layer Boundary Violations
The domain layer directly depends on Room entities (`Expense` in `BlockPartyDay.kt`). This is a systemic issue in the codebase (31 files in the domain layer import `data.database.entity.Expense`), but for domain *model* files it's particularly problematic since models should be the most stable, dependency-free classes.

### 2. Copy Semantics Trap in Sealed Class Hierarchies
`UpcomingItem.Recurring` and `UpcomingItem.Planned` both override abstract properties with fixed `val` assignments in the class body (not constructor parameters). This is a known Kotlin pitfall — `data class copy()` only copies constructor parameters, so overridden body properties become stale after `copy()`.

### 3. Sentinel Values as Enum Properties
Both `ForecastHorizon.REST_OF_MONTH.days = 0` and `RecurrenceFrequency.IRREGULAR.days = 0` use zero as a sentinel meaning "not applicable". This creates API traps where callers might use the property in arithmetic without knowing the convention.

### 4. Model Duplication and Enum Proliferation
The codebase has parallel model hierarchies for the same concepts (`PeriodRange` × 2, `SavingsGoal` × 2, `GoalProtectionLevel` × 2, `RiskLevel` × 5). While domain/entity separation is correct architecture, the lack of shared vocabulary and the 5 separate risk-level enums creates maintenance burden and mapping bugs.

### 5. Locale-Sensitive String Formatting
`MonteCarloBudgetImpact.formatCurrency()` doesn't specify a `Locale`, while the rest of the codebase (e.g., `NarrativeGenerator`) correctly uses `Locale.US`. This inconsistency means the same number formats differently depending on which code path formats it.
