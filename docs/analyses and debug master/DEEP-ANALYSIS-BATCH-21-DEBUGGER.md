## Key Patterns

1. **Insufficient Thread Safety in Shared Mutable State**: Multiple classes (`NotificationCaptureService`, `RecommendationStateManager`, `RecommendationCacheService`) use shared mutable state accessed from multiple coroutines/threads. The synchronization mechanisms are inconsistent — some use `Mutex`, some use `synchronizedMap`, some use `@Volatile`, but none achieve full atomicity for compound check-then-act operations.

2. **Silent Error Swallowing**: A pattern of empty `catch (e: Exception) { }` blocks exists in `RecommendationInvalidator`, `RecommendationStateManager`, and the `DailyBriefingWorker` returns `Result.success()` even on failure. This makes production debugging nearly impossible and can mask data corruption.

3. **Worker Retry Strategy Inconsistency**: `DailyBriefingWorker` returns `Result.success()` on all errors (never retries), `ReceiptMatchingWorker` and `WarrantyExpirationWorker` return `Result.retry()` on errors. There is no consistent retry/backoff strategy across workers, and no attempt count limit on retries.

4. **NotificationIdGenerator Range Overflow**: The notification ID generator uses fixed ranges with arithmetic offsets that can overflow into adjacent ranges. The `forWarranty()` method with `daysOffset=5000` can produce IDs in the receipt range, and `fromLong()` can produce negative offsets. This is a systemic design issue in the range allocation scheme.

5. **Package/Location Mismatch**: `ReceiptMatchingWorker.kt` is physically in `service/receiptmatching/` but declares `package com.yourname.expensetracker.data.repository`. This suggests it was moved without updating the package declaration, or the file was copy-pasted from another location. This can cause subtle issues with Hilt worker injection and IDE navigation.

6. **Service Lifecycle Fragility**: `NotificationCaptureService` has an aggressive 1-minute restart alarm, calls `stopForeground()` after coroutine cancellation (wrong order), and doesn't properly guard against lifecycle edge cases on OEM ROMs. The service restart strategy should use WorkManager rather than raw AlarmManager for better battery compliance.
