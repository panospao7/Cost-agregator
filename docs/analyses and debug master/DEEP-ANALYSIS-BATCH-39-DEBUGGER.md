## Key Patterns

### 1. Hand-Rolled Serialization (DebugData.toJson)
The manual JSON construction in `DebugData.toJson()` is the most pervasive source of bugs in this batch. It fails to properly escape backslashes, tabs, carriage returns, and other control characters per the JSON specification. This is a classic antipattern — the codebase already uses serialization libraries elsewhere.

### 2. String-Based Enum Matching (BillReminderManager)
`BillReminderManager` uses `.name` string matching instead of exhaustive `when` on the `RecurrenceFrequency` enum. This causes silent fallthrough for `SEMI_ANNUALLY` and `IRREGULAR`, producing **6x overestimates** in monthly billing totals and incorrect next-date calculations.

### 3. Unformatted Double Output (All Exporters + IIF)
All three accounting exporters use Kotlin's default `Double.toString()` for financial amounts. This can produce scientific notation (`1.0E7`), excessive decimal places (`0.30000000000000004`), or inconsistent precision (`100.0` vs `99.99`).

### 4. Thread-Unsafe SimpleDateFormat
All three exporters store `SimpleDateFormat` as instance fields. While the exporters aren't annotated as `@Singleton`, if they're reused across coroutines (common in Android ViewModels), concurrent access will corrupt date formatting.

### 5. Placeholder Code Shipping Risk (BankApiIntegration)
The bank integration contains placeholder OAuth URLs pointing to `example.com`, hardcoded demo tokens, and mock transaction generation. While clearly marked as placeholders, there's no compile-time guard or feature flag to prevent accidental deployment.

### 6. Sign/Type Loss in Bank Sync Pipeline
`BankApiIntegration` applies `abs()` to all transaction amounts and hardcodes `TransactionType.PURCHASE`, losing the ability to distinguish deposits from purchases. This means bank-synced income, refunds, and transfers all appear as purchases.
