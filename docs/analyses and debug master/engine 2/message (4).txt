# 4. Original final-gate issue reconciliation

## E1-FINAL-001 — Vodafone CU misclassified as INTERNET

Previous status: **RED**  
Current status: **FIXED**

### Evidence

`analyzeNegotiationOpportunities()` now passes the raw merchant:

```kotlin
val marketRate = findMarketRate(subscription.merchant)
```

not the pre-normalized merchant key.

`detectServiceType()` now uses both:

```kotlin
val raw = merchantName.uppercase()
val key = providerMatchKey(merchantName)
```

and checks mobile-specific normalized keys first:

```kotlin
VODAFONECU
WHATSUP
COSMOTEMOBILE
VODAFONEMOBILE
MOBILE
CELL
PHONE
```

The INTERNET branch no longer treats plain provider roots like `VODAFONE` or `COSMOTE` as internet. It requires internet-specific keywords like:

```text
INTERNET
FIBER
VDSL
BROADBAND
COSMOTEFIBER
VODAFONEFIBER
NOVAFIBER
```

### Test evidence

`NegotiationEngineTest` now stubs and verifies exact provider type:

```text
VODAFONE CU -> MOBILE
Cosmote Fiber -> INTERNET
```

The test verifies `provider.getRates(MOBILE, "GR", "EUR")` and verifies `INTERNET` is not called for the Vodafone CU case.

### Pipeline impact

Positive. Mobile subscriptions should no longer receive internet benchmark rates.

### Verdict

**GREEN**

# 5. Engine correctness review

## What is correct now

### Negotiation detection

Now much safer:

```text
Vodafone CU -> MOBILE
Cosmote Fiber -> INTERNET
DEI Energy -> ENERGY -> skipped
EYDAP -> WATER
Netflix -> STREAMING
```

The dangerous previous pattern:

```text
plain VODAFONE/COSMOTE -> INTERNET
```

was removed.

### Quote matching

The engine now uses normalized quote/provider keys:

```kotlin
providerMatchKey(merchantName)
providerMatchKey(quote.providerName)
providerRootMatches(...)
```

This should prevent common punctuation/spacing mismatch.

### Energy

ENERGY is explicitly skipped. This is correct until a consumption-aware model exists.

### Non-EUR

Non-EUR subscriptions are skipped. This is correct while market rates are EUR/GR-only.

### Outcome recording

`recordNegotiationOutcome()` now has a much cleaner structure:

1. check write barrier
2. get subscription
3. validate money/currency/outcome
4. insert outcome
5. update price history/subscription for success/partial
6. return `Result`
7. rethrow cancellation
8. return failure for non-cancellation exceptions

This matches the method contract.

# 6. Remaining issues / hardening items

## E1-REMAINING-001 — Existing lowercase subscription currency can block outcome recording

Severity: **P2 / legacy-data hardening**

### Evidence

`validateNegotiationOutcomeInput()` checks:

```kotlin
currency.matches(Regex("^[A-Z]{3}$"))
```

But it receives:

```kotlin
subscription.currency
```

If a legacy subscription has:

```text
"eur"
```

then outcome recording fails even though the value is semantically valid.

`analyzeNegotiationOpportunities()` normalizes currency using `trim().uppercase()`, but `recordNegotiationOutcome()` validation does not normalize before validating/persisting.

### Recommended fix

Normalize once:

```kotlin
val normalizedCurrency = subscription.currency.trim().uppercase()
validateNegotiationOutcomeInput(..., currency = normalizedCurrency)
...
NegotiationOutcomeEntity(currency = normalizedCurrency)
SubscriptionPriceHistory(currency = normalizedCurrency)
```

### Test

```text
recordNegotiationOutcome_lowercaseEurCurrency_normalizesAndSucceeds()
```

### Blocking?

No, because new subscription validation likely writes uppercase. But for recovered/legacy data, this is worth fixing.

---

## E1-REMAINING-002 — Existing invalid subscription amount can produce bad opportunities

Severity: **P2 / legacy-data hardening**

### Evidence

`analyzeNegotiationOpportunities()` does not validate:

```text
subscription.amount finite
subscription.amount > 0
```

before creating opportunities.

If legacy data contains:

```text
amount = Infinity
amount = NaN
amount = negative
```

then `monthlyEquivalent()` can return invalid values or zero.

New subscription creation validation likely prevents this going forward, but old DB rows can still exist.

### Recommended fix

Before market lookup:

```kotlin
if (!subscription.amount.isFinite() || subscription.amount <= 0.0) {
    Timber.w("Skipping negotiation for invalid subscription amount id=%d", subscription.id)
    return@forEach
}
```

### Tests

```text
nanSubscriptionAmount_skipsNegotiation()
infiniteSubscriptionAmount_skipsNegotiation()
negativeSubscriptionAmount_skipsNegotiation()
```

### Blocking?

No, but it aligns with the “dirty data -> warning/skip, not bad result” rule.

---

## E1-REMAINING-003 — Provider quote values are trusted without validation

Severity: **P2**

### Evidence

`findMarketRate()` accepts provider quotes and creates `MarketRate` without checking:

```text
averageMonthlyPrice finite > 0
competitiveMonthlyPrice finite > 0
bestMonthlyPrice finite > 0
```

If a provider returns `0`, `NaN`, or `Infinity`, later scoring can divide by bad values:

```kotlin
(currentPrice - marketRate.competitivePrice) / marketRate.competitivePrice
```

### Recommended fix

Filter quotes:

```kotlin
val validQuotes = result.quotes.filter {
    it.averageMonthlyPrice.isFinite() && it.averageMonthlyPrice > 0.0 &&
    it.competitiveMonthlyPrice.isFinite() && it.competitiveMonthlyPrice > 0.0 &&
    it.bestMonthlyPrice.isFinite() && it.bestMonthlyPrice > 0.0
}
if (validQuotes.isEmpty()) return null
```

### Tests

```text
providerReturnsZeroCompetitivePrice_skipsQuote()
providerReturnsNaNQuote_skipsQuote()
providerReturnsOnlyInvalidQuotes_noOpportunity()
```

### Blocking?

No for the static provider, but useful for provider abstraction safety.

---

## E1-REMAINING-004 — Best quote fallback is `quotes.first()`

Severity: **P3 / behavior refinement**

### Evidence

If no provider name matches merchant key/root, the engine falls back to:

```kotlin
quotes.first()
```

This may select an arbitrary provider if provider order changes.

### Better fallback

Use lowest competitive price or average benchmark depending desired meaning:

```kotlin
quotes.minByOrNull { it.competitiveMonthlyPrice }
```

or explicitly call it a market benchmark rather than “current provider.”

### Blocking?

No. Current tests cover main provider-root cases.

---

## E1-REMAINING-005 — Warranty diagnostic still uses sentinel `warrantyId = -1`

Severity: **P2 / observability semantics**

This was already known.

`WarrantyTrackerRepository` now avoids writing return-window events with wrong receipt/return-window IDs as warranty IDs, which is good.

But very-low-confidence warranty discard writes:

```kotlin
WarrantyLifecycleEvent(warrantyId = -1L, eventType = AI_EXTRACTION_DISCARDED, ...)
```

This is durable, but semantically weak. It would be better as:

```text
PipelineDiagnosticEvent or ReceiptLifecycleEvent with receiptId
```

Blocking?

No. Acceptable short-term if documented as diagnostic workaround.
