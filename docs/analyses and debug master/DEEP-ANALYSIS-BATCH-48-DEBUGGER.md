## Key Patterns

### 1. Divergent duplicate logic across use cases
The most systemic issue is duplicated entity-to-domain mapping and forecast computation logic between `CalculateFinancialForecastUseCase` and the dashboard pipeline. This creates a dangerous situation where bug fixes in one path don't propagate to the other, resulting in inconsistent forecast data depending on which entry point the user reaches.

### 2. Risk tier classification inconsistency
The risk tier determination uses OR-based cascading in the implementation but documents AND-based logic. This means risk tiers are consistently inflated — any single elevated metric (either overrun percentage OR probability) bumps the tier up, even if the other metric is fine. The documentation across two files needs alignment.

### 3. Hardcoded defaults that distort calculations
`CalculateFinancialForecastUseCase` hardcodes `GoalProtectionLevel.TRACKING`, `projectedTotal = monthSpent`, and `pastSumDaily = emptyList()`. These defaults silently produce degraded results rather than failing visibly, making the bugs hard to detect.

### 4. Testability bypassed by direct infrastructure access
`DashboardContractsAdapter.kt` uses `System.currentTimeMillis()` and `ComputeMoneyRadarUseCase` directly accesses `AnomalyAlertDao`, bypassing the injected `TimeProvider` pattern and repository abstraction layer respectively.

### 5. Private extension property shadowing entity property
`MonthlySavingsSweepUseCase` redefines `effectiveAmount` as a private extension on `Expense`, creating a hidden divergence risk. This pattern should be avoided in favor of using the entity's canonical property.
