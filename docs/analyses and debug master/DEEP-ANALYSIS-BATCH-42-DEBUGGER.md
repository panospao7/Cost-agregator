## Key Patterns

### 1. Fire-and-Forget Coroutine Anti-Pattern (Critical)
The `ExpenseCategoryClassifier.saveModelInternal()` launches a fire-and-forget coroutine for file I/O while the caller assumes the save completed. This is the single most dangerous pattern: data loss on app kill, silent I/O errors, and potential concurrent file writes.

### 2. Visibility of `@Volatile` Flags (Recurring Medium)
Both `ExpenseCategoryClassifier.isLoaded` and `HybridExpenseClassifier.initialized` are plain `var` fields checked outside their respective mutexes. On multi-core ARM devices (common on Android), these reads may see stale values due to CPU cache coherency.

### 3. Grid Bucketing with Truncation (Systemic Medium)
All four location engines use `.toLong()` for grid snapping, which truncates toward zero rather than flooring. This is dormant for Greece (all positive coords) but is a latent bug for any expansion to southern/western hemisphere regions.

### 4. Training/Inference Feature Mismatch (ML)
The ML pipeline extracts rich features (`amountBucket`, `dayOfWeek`, `hourOfDay`, etc.) but the Naive Bayes classifier only uses `merchantTokens`. Additionally, `extractFromNotification` uses current time while `extractFromExpense` uses the expense's date, creating temporal drift between training and inference.

### 5. Inconsistent Input Types Across Engines
`TravelDetectionEngine` and `AreaSpendingEngine` consume `List<Expense>` directly, while `SpendingHeatmapEngine` and `LocationInsightsEngine` consume `List<LocatedExpense>`. This forces ViewModels to maintain two mapping paths and increases the risk of using `amount` vs `effectiveAmount` inconsistently.
