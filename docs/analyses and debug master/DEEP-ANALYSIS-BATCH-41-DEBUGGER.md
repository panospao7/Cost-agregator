## Key Patterns

### 1. Inconsistent `amount` vs `effectiveAmount` Usage
`RecurringIncomeTracker` uses raw `amount` in multiple places (lines 59, 113-115) while the rest of the codebase has migrated to `effectiveAmount`. This systematically miscounts shared expenses and "not mine" transactions in income tracking.

### 2. Duplicate Time Utility Implementations
`FinancialHealthCalculator` and `RecurringIncomeTracker` both implement their own `getStartOfMonth`, `getStartOfDay`, `getStartOfWeek` functions instead of using the centralized `TimePeriodUtils`. This leads to subtle differences (missing millisecond reset, different week start days) that cause boundary bugs.

### 3. Two Parallel Health Score Systems
`FinancialHealthCalculator` and `FinancialHealthScoreV2` are completely independent health scoring systems with different methodologies, different component weights, and incompatible score scales (Calculator caps at ~75, V2 uses proper 0-100).

### 4. Missing `TimeProvider` Injection in InvestmentTracker
`InvestmentTracker` uses `System.currentTimeMillis()` directly in 4 places, breaking the testability pattern established by all other domain components in this batch.

### 5. Fire-and-Forget Persistence
Both `TransactionClassifier` and `ExpenseCategoryClassifier` use debounced fire-and-forget saves to disk. `ExpenseCategoryClassifier.saveModelInternal()` launches a coroutine to write while releasing the mutex, creating a window where a concurrent load reads a partially-written file.
