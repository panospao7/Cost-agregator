## Key Patterns

### 1. Fake Tests / No Production Code Coverage (Issues #1, #2, #3, #5, #16, #17)
**This is the most severe pattern.** Six findings involve test files that define local helper classes and simulation methods, then test those instead of actual production code. The `NotificationProcessingPipelineStressTest` is the worst offender — it contains a tautological assertion (`result != null || result == null`) that literally cannot fail, and its entire test surface exercises zero production classes. `TransactionRollbackTest` and `ExpenseDaoBoundaryConsistencyTest` similarly provide zero Room/DAO coverage. **These tests inflate coverage metrics while providing no safety net.** Recommendation: delete or rewrite against real production classes with mocked dependencies.

### 2. Test Pollution / Missing Cleanup (Issues #6, #7, #8, #9)
Four test files override global JVM state (`Dispatchers.setMain`, `mockkStatic`) without restoring it in `@After`. This causes non-deterministic test failures when the test suite runs in a specific order. The pattern is insidious: tests pass in isolation but fail when run together, or — worse — pass together but mask bugs because a leaked mock intercepts production calls. **Recommendation:** Every `@Before` that mutates global state must have a matching `@After` that restores it. Consider a shared base test class or JUnit `@Rule` that enforces this.

### 3. Non-deterministic Time Dependencies (Issues #10, #11, #12)
Multiple test files use `System.currentTimeMillis()` for entity construction and mock setup. This makes tests date-sensitive — they may behave differently near midnight, month boundaries, or year boundaries. The `BudgetRolloverTest` is particularly vulnerable since budget periods are inherently time-bounded. **Recommendation:** Always use fixed timestamps in tests. Inject `Clock` or `TimeProvider` interfaces for production code.

### 4. Missing Migration Tests (Structural Gap)
The app is at **schema version 70**, yet no migration tests exist in the `data/database/` test directory. Room migration tests (`MigrationTestHelper`) are essential for verifying that `ALTER TABLE` statements, data transformations, and index changes work correctly across all version transitions. A single migration bug can corrupt user data on app update. **Recommendation:** Add `MigrationTest` class covering at least the last 5-10 schema versions.

### 5. Mock-Only DAO Tests (Issues #20, #22)
DAO tests mock the interface and verify that "when mock returns X, code does Y." This is circular — it tests that MockK works, not that the SQL query is correct. The only way to verify `@Query` SQL is with an in-memory Room database in `androidTest/`. **Recommendation:** Supplement unit tests with instrumented DAO tests for all complex queries.

### 6. Disabled Stress Tests (Issue #21)
Multiple `@Ignore`-annotated stress tests across the repository test directory represent dead code. They don't run in CI, can't catch regressions, and will silently rot as the codebase evolves. **Recommendation:** Fix or delete — `@Ignore` without a linked ticket is a commitment to never fix.

---

## Verdict

**NEEDS SIGNIFICANT REWORK.** The test suite has fundamental integrity problems: critical tests that exercise no production code, tautological assertions that cannot fail, and global state leaks that make the suite order-dependent. The absence of migration tests at schema version 70 is a serious gap for a production app. While some test files (e.g., `MultiCurrencyRepositoryTest`, `FinancialWeatherRepositoryTest`, `ExpenseRepositoryTest`) demonstrate proper patterns with correct mocking, dispatcher usage, and meaningful assertions, they are outnumbered by problematic files. Priority should be: (1) delete/rewrite fake tests, (2) add `@After` cleanup to all test classes, (3) add migration tests, (4) replace `System.currentTimeMillis()` with fixed values.
