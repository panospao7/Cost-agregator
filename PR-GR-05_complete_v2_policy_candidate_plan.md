# PR-GR-05 — Produce a complete v2 ownership-policy candidate

## Agent mission

Produce a reproducible, strict v2 candidate plus an auditable accounting record for **every** legacy ownership-policy row.

“Complete” in this PR means:

1. every legacy input row has exactly one reviewed disposition;
2. every emitted v2 row has exact callable and DAO identity;
3. every omission is explicit, controlled, and reviewable;
4. no source mutation is silently converted into authorization;
5. the checked-in candidate is generated by tooling, never hand-edited.

This is still a **candidate-only** PR. It must not activate v2, update the ratchet baseline, or make a green-guard claim.

## Current-state anchor

At the starting branch state, a strict v2 model already exists and defines identity as:

`path + ownerFqcn + kind + method + receiver + ordered parameterTypes + daoAccessor + daoFqcn + operation`.

The active policy remains legacy-shaped, while the candidate is a small generated v2 subset. ([raw.githubusercontent.com](https://raw.githubusercontent.com/panospao7/Cost-agregator/e7b7597098dc2e7ac0a35f8342b20f9f4a420f41/scripts/db_guard/policy_model.py))

## Preconditions / hard stops

Before editing:

1. Record `START_SHA`, tree SHA, clean status, active-policy hash, candidate hash, and baseline hash.
2. Run the GR-00 capture workflow for the actual start SHA.
3. Confirm inventory-only is trusted, diagnostic-free, and exits `0`.
4. Confirm GR-02 candidate generation, GR-03/03R source-root checks, and GR-04 structural-manifest tests pass.
5. Read actual current module APIs. Reuse:
   - `scripts/db_guard/policy_v2_candidate.py`
   - `scripts/db_guard/policy_model.py`
   - `scripts/db_guard/policy_v2_loader.py`
   - `scripts/db_guard/source_roots.py`
   - shared Room inventory / declaration / DAO-resolution APIs.

Stop and report instead of guessing if:

- inventory-only is untrusted;
- the active legacy policy cannot be parsed;
- a source-root diagnostic occurs;
- a callable, DAO accessor, DAO FQCN, or target mutation is ambiguous;
- a proposed fix would require changing production Kotlin, activating v2, or updating a baseline.

## Required deliverables

### 1. Complete-accounting artifact

Add a tracked, deterministic artifact, for example:

`config/guards/db_ownership_policy.signatures.candidate.accounting.json`

It must be generated from the same run as the candidate and contain:

- schema/version;
- source legacy-policy repository-relative path and SHA-256;
- source tree SHA;
- candidate SHA-256;
- legacy input count;
- one record for every legacy row index;
- exact outcome:
  - `RESOLVED`
  - `UNRESOLVED`
- controlled unresolved status;
- reviewed action;
- zero or more emitted v2 mutation keys;
- no absolute paths, raw source, SQL, exception text, user data, or secret values.

Required invariants:

- every integer in `0..input_count-1` appears exactly once;
- no duplicate legacy index;
- every candidate mutation key maps to one or more legacy indices;
- every `RESOLVED` record maps to at least one candidate mutation key;
- every candidate entry is represented in the accounting artifact;
- unresolved rows never create candidate entries;
- all ordering is deterministic.

Do not introduce a vague “other” category. Extend the closed status catalog when needed.

### 2. Explicit source-mutation coverage section

The accounting artifact must also record discovered direct Room mutations as:

- `COVERED_BY_RESOLVED_LEGACY_ROW`;
- `OBSERVED_NOT_IN_LEGACY_POLICY`;
- `OBSERVED_BUT_UNRESOLVED`;
- `UNRESOLVED_ANALYZER_INPUT`.

This section is evidence, not authorization. In particular, an observed mutation absent from legacy policy must **not** be added to the v2 candidate in this PR. It becomes a real finding or a later reviewed policy decision in GR-08.

### 3. Candidate contract

The generated candidate must:

- use `schemaVersion: 2`;
- round-trip through `load_policy_v2`;
- contain only v2 fields;
- contain one entry per exact mutation key;
- use full owner FQCN, exact callable kind, exact receiver, ordered normalized parameter types, exact DAO accessor, exact DAO FQCN, and exact Room operation;
- contain no legacy `class`, `daos`, nested `signature`, `barrier_required`, `barrier_via`, wildcard, or simple-name DAO identity;
- be canonical, byte-reproducible, and newline-normalized.

### 4. Barrier-mode classification

`barrierMode` remains metadata only. It must never be presented as control-flow proof.

Use only this conservative mapping:

| Evidence | Candidate result |
|---|---|
| Exact local direct barrier syntax before mutation | `direct` |
| Exact legacy/helper classification, but no direct proof | `helper` |
| Exact legacy WorkerExecutionGuard classification | `workerMediated` |
| Contradictory, missing, or ambiguous evidence | `UNRESOLVED: BARRIER_MODE_UNRESOLVED` |

GR-05 must not implement dominance, helper-call-graph, or worker-root proof. Those belong after GR-09.

## Implementation sequence

### Step 1 — Freeze and inspect

Run and preserve:

```bash
git status --short
git rev-parse HEAD
git rev-parse HEAD^{tree}
git hash-object config/guards/db_ownership_policy.yml
git hash-object config/guards/db_ownership_policy.signatures.candidate.yml
git hash-object config/baselines/db_access.json
```

Run the candidate tool in check mode and save its report before changing code.

### Step 2 — Add accounting model and invariants first

Write tests for:

- every source index accounted for exactly once;
- resolved-to-candidate and candidate-to-resolved crosswalk equality;
- deterministic ordering;
- rejected unknown statuses;
- no candidate row for unresolved input;
- no untracked source mutation omission.

Do not begin bulk conversion until these tests exist.

### Step 3 — Resolve legacy rows with exact callable evidence

For each legacy row:

1. Canonicalize and root-validate its path.
2. Resolve exact owner FQCN; legacy class name is only a hint.
3. Resolve exact callable identity.
4. Discover mutations only inside that callable body/range.
5. Resolve bare accessor identity and exact DAO FQCN.
6. Resolve the exact Room mutator overload/operation.
7. Split one legacy row into multiple exact v2 rows only where source proves distinct mutation keys.
8. Record `RESOLVED` only after all emitted rows pass the v2 loader.

Never borrow evidence from:

- a sibling overload;
- another same-simple-name class;
- another nested owner;
- another file;
- comments/strings;
- a safe call or complex receiver expression;
- an arbitrary DAO with the same simple name.

### Step 4 — Classify, do not hide, unresolved rows

Each unresolved record must include:

- controlled status;
- bounded detail;
- next action;
- owner;
- linked issue;
- whether it blocks GR-07.

Minimum statuses:

```text
OWNER_MISSING
OWNER_AMBIGUOUS
CALLABLE_MISSING
CALLABLE_AMBIGUOUS
CALLABLE_KIND_UNSUPPORTED
DAO_IDENTITY_UNRESOLVED
DAO_TARGET_AMBIGUOUS
MUTATION_PAIR_MISSING
BARRIER_MODE_UNRESOLVED
SOURCE_ROOT_UNRESOLVED
PARSER_UNSUPPORTED
```

A stale-looking legacy row is not silently discarded. Record it as unresolved until a reviewer explicitly approves its later removal.

### Step 5 — Keep parser repairs narrow

A parser/resolver repair is allowed only when all are true:

1. it unlocks a named unresolved row;
2. a synthetic negative fixture proves the previous false failure;
3. a neighboring forbidden pattern still fails closed;
4. it does not change active scanner authorization;
5. it does not broaden fallback behavior.

If more than three unrelated parser families emerge, stop GR-05 and create a separate analyzer-repair PR before continuing.

### Step 6 — Generate tracked artifacts only through the CLI

Generate candidate and accounting output into `build/guard-debug/gr05/` first. Validate there, then copy/replace tracked files only through a dedicated generator mode or an explicit reviewed promotion command.

The generator must reject:

- output collision with active policy;
- duplicate v2 mutation key;
- malformed output;
- candidate/accounting mismatch;
- partial write;
- non-deterministic ordering.

### Step 7 — Review the unresolved population

Create a review table in documentation or the accounting artifact identifying:

- count by status;
- activation-blocking count;
- source-mutation coverage count;
- every legacy row’s disposition;
- explicit statement that unresolved rows are not authorization.

No “resolved percentage” may be used as a pass criterion.

## Required test matrix

### Identity and conversion

1. nested owner FQCN;
2. same simple class name in two packages;
3. same method name in two owners;
4. overloaded functions with distinct parameters;
5. nullability difference;
6. parameter order difference;
7. extension receiver difference;
8. top-level function, constructor, initializer, getter, setter where supported;
9. one callable → multiple DAO operations;
10. one legacy multi-DAO row → exact split rows;
11. exact DAO FQCN collision;
12. exact DAO accessor mismatch;
13. comments/strings do not count;
14. safe-call and expression receivers remain unresolved;
15. duplicate resulting mutation key fails exit `2`.

### Accounting

1. every input row is represented exactly once;
2. candidate ↔ accounting crosswalk is bijective at mutation-key level;
3. stale/missing mutation remains unresolved;
4. source mutation absent from legacy policy is visible;
5. all status values are registered;
6. output is deterministic across two fixture runs;
7. candidate and accounting writes are atomic;
8. no absolute paths or raw source leak.

### Repository regression

1. checked-in candidate round-trips through v2 loader;
2. fresh generation byte-matches tracked candidate;
3. fresh generation byte-matches tracked accounting artifact;
4. active legacy policy is byte-identical before/after;
5. baseline is byte-identical before/after;
6. normal DB CLI remains blocked for the pre-activation authority path, not due to a newly introduced error.
