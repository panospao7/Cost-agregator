# Taste
- Pins all subagents (specialist-coder, swarm-coder, tester, documentor, scout) to model `meta/muse-spark-1.3-contributor` — pass the model explicitly at launch time for every subagent type. Confidence: 0.95
- Prefers main-session orchestrator model to be glm-5.3-flash. Confidence: 0.9
- Prefers reviewer-strict agent pinned to zai-org/GLM-5.3. Confidence: 0.9
- Development is plan-doc-driven: user maintains numbered PR plan documents (e.g., `docs/guardrails/PR-XX_*_plan.md`) plus roadmap/charter/state files and explicitly asks the agent to read those docs for full context before implementing anything. Confidence: 0.85
- For design-level chunks that change engine contracts/architecture (e.g., GR-14 Contract v2: proof-engine contract + structural engine + scanner + labelled-return handling) — and likewise for smaller changes to the guardrail analysis/proof engine's classification behavior — enter plan mode first: explore the design and current code read-only, then write a plan for the user's sign-off before touching anything ("lets rite the plan"). Confidence: 0.75
- On a new task, expects the agent to first review recent git history (~20–50 commits) to understand the process and current code before acting. Confidence: 0.8
- Works across multiple git worktrees in parallel with the main tree (e.g., a `GR00-worktree` on a separate branch like `gr-00-local`) — when referenced code/branches are missing from the main checkout, check the worktrees before concluding work doesn't exist. Confidence: 0.7
- A fresh git worktree lacks the gitignored `local.properties`, so Gradle validation fails with "SDK location not found" — create a minimal one containing only `sdk.dir` (never copy secrets/API keys from the main tree). Confidence: 0.6
- Expects the agent to verify plan docs against actual repo state (committed vs in-flight/uncommitted work) and report an accurate progress picture before proposing next steps. Confidence: 0.65

## Subagent management
- Expects the agent to leverage available agents/tools during plan execution rather than working solo ("you have also agents/tools to help you") — e.g., activate the orchestrated-batch skill for an approved plan batch and launch parallel scout subagents for precondition reconnaissance. Confidence: 0.75
- When a scout subagent hits its turn limit mid-reconnaissance, the user prefers relaunching the scout (pinned to muse-spark) over finishing the recon in the main session; finishing directly in the main session is the fallback. Confidence: 0.7
- Launch scout subagents with a large step budget (~200 turns) regardless of task size — "give it like 200 steps or something big regardless" — so reconnaissance never dies at default turn limits; frame the scout prompt with "you have a large budget — be exhaustive and precise". Confidence: 0.9
- When a specialist-coder subagent stalls or stops early on a large task, first check what partial work landed (git status / dir listing), then relaunch it with model `z-ai/glm-5.3-flash` (exact catalog id) and a note to reconcile the partial files left on disk. Confidence: 0.9
- If subagents keep stalling on a batch anyway (Windows cmd shell-quoting over inline code snippets is the usual cause), stop burning agent runs and finish the batch directly with write_file plus scratchpad scripts. Confidence: 0.85
- For large implementation batches, give subagents fully-inline specs, cap exploration ("look at at most N files"), say "WRITE FILES EARLY", and run the tests yourself rather than letting the agent drive the shell. Confidence: 0.85
- Parallelize independent subagent tasks in one launch block (e.g., read-only scout verification + documentor drafting) and gate commits on the scout's verdict. Confidence: 0.75
- Review gates must actually complete: when a built-in reviewer hits its turn limit, create a custom agent in `.commandcode/agents/*.md` with `maxTurns: 200` (default is 100, no documented upper bound), a pinned model, read-only tools, and a required VERDICT block — custom agents are picked up live; then fix any FAIL items and re-run the reviewer until PASS. Confidence: 0.9

## Windows cmd environment
- The shell is Windows cmd, not bash: heredocs don't work — write long commit messages to a temp file and commit with `git commit -F <file>`; capture exit codes in chained commands with `call echo EXIT=^%ERRORLEVEL^%` and chain with `&`. Confidence: 0.9
- For multi-step Python debugging, write a scratchpad script into the session temp dir and run it instead of fighting complex inline `python -c` quoting on cmd. Confidence: 0.9

## Gradle validation
- Prefers targeted Gradle validation over whole-suite runs: use `:app:compileDebugKotlin` to verify production (Kotlin) changes compile, and `--tests "*SpecificClass*"` filters to run individual test classes. Confidence: 0.95
- Never run the full unfiltered Android/unit test suite (`:app:testDebugUnitTest` with no `--tests` filter): it has many known pre-existing failures and test compilation can hang for a very long time. Confidence: 0.95

## Slice-commit gates (guardrail program)
- Gate every slice commit: preservation diff must be empty (app/src/main, config/, baselines, control-plane scripts, .github/workflows), parity/pin suites green, and parity proven before committing. Confidence: 0.9
- Evidence artifacts must be reproducible: run twice and require byte-identical output before committing. Confidence: 0.85
- Guardrail engine-classification changes follow a fixture-first admission protocol: a written plan naming a closed target set; a pin fixture that fails before the fix and passes after (A/B-attributed); a before/after shadow-report delta showing exactly the intended row(s) flip with zero regressions and zero unexplained changes; and owner sign-off — with policy bytes, allowlists, and expiries left untouched unless the change is itself a policy decision. Confidence: 0.7
- When a legitimate engine/classification change flips an existing pin fixture's expected outcome, update the fixture to the new truth and say so explicitly (e.g. that it no longer pins the old behaviour) rather than weakening or suppressing the change to keep the fixture green — a newly-reachable unguarded writer must surface as a counterexample, not stay hidden behind an uncertain edge. Confidence: 0.7
- A projection is a lower bound on scope: after implementing a Step-0-projected change, re-capture and verify the real delta rather than assuming the projection held — the implementation may be broader than what was projected (e.g. the projection textually excluded `this::` while the fix handled it), and the fixture corpus is what surfaces the difference. Confidence: 0.65
- Treat a matching failure count as insufficient evidence: prove the pre-existing failing tests are the *identical set* by listing them, since equal counts can hide a swap. Confidence: 0.65
- Before implementing a risky engine/classification change, pre-validate its blast radius with a read-only projection: simulate the change in-memory (e.g., monkey-patch the resolver, re-run the full analysis, diff the whole board) and make that measurement the plan's FIRST mandatory step ("Step 0" gate), hard-stopping and escalating to the owner if it surfaces unexpected outcomes (e.g., rows flipping to counterexample) instead of implementing first and triaging the fallout later. Confidence: 0.65
- Commit style: `feat(db): GR-XX S# - summary` plus a body with parity/validation/preservation evidence and a `Co-authored-by: CommandCodeBot <noreply@commandcode.ai>` trailer (via commit-message file). Confidence: 0.85
- Uses Conventional Commits throughout their own history — `type(scope): summary` with lowercase types like `docs(...)`, `fix(...)`, `chore` (scope sometimes omitted). Confidence: 0.7
- On plan ambiguity, choose the MORE conservative interpretation and document the choice in the module docstring; implementation must match the plan/ADR closed vocabularies exactly. Confidence: 0.9
- Tests are pytest, import via the `scripts.*` package like sibling tests, fully deterministic, assert model content only (never dominance verdicts), and report outputs must never carry raw source, exception text, or absolute paths. Confidence: 0.85
- Docs are truth-synced: ADR/status lines state exactly what is implemented (mark PARTIAL while in-flight, update when slices land) and never claim unimplemented artifacts exist. Confidence: 0.85
- Treat a negative result as a deliverable: when verification falsifies a hypothesis or a proposed change, record what was tested and falsified together with the evidence (enforcement points, pinning tests, measured counts) so it is not re-opened without new evidence, and correct the report/config to state the refutation rather than making the originally proposed change ("refutation over change"). Confidence: 0.7
- When a plan enumerates adversarial cases (e.g., the 12 barrier placements), implement every enumerated case as its own named pytest fixture — a full matrix (TestProvenPlacements/TestCounterexamplePlacements/TestUnsupportedRoutes), not a sampled few. Confidence: 0.7
- Fix discovered pre-existing defects at their root (e.g., GR-11 if-body CFG wiring fixed in the tokenizer, not worked around in the new consumer), then re-run the full suite and regenerate all downstream evidence artifacts (shadow pair, corpus, inventory). Confidence: 0.7
- Fail-closed reporting: guard CLIs must emit every policy row exactly once with an explicit outcome (PROVEN / COUNTEREXAMPLE / UNSUPPORTED / INFRASTRUCTURE_FAILURE) — uncorrelatable or missing rows are never silently dropped — and every pipeline parsing the same callables must use identical gates and site inputs. Confidence: 0.7

## Communication
- User steers with terse minimal nudges ("continue", "so wha is next", "WHAT IS NEXT TO DO") after stalls, decision points, or batch completion — treat that as approval to self-direct and deliver a detailed evidence-backed status report at the batch boundary (counts, SHAs, artifacts, precise blocker reasons, and a prioritized next-step roadmap with a continue/pause question). Confidence: 0.8
- Validated work is left uncommitted until the user gives an explicit go-ahead; a terse "commit and proceed" (typos and all, e.g. "commit kai proceed") means commit the batch (with the usual commit-message file + trailer) and immediately start the next prioritized item without further confirmation. Confidence: 0.7
- Distrusts third-party LLM proxies by default and prefers empirical verification of reasoning ability over trusting config/model names — log forensics for Reasoning items/token counts plus effort-knob A/B probes measuring reasoning tokens and answer quality — and re-runs the same benchmark after switching providers to compare. Confidence: 0.8
- Redacts live secrets when sharing configs in chat/logs (e.g., partially redacting API keys in auth.json) — pasting live secrets into chat logs is a bad habit, even in own sessions. Confidence: 0.9
